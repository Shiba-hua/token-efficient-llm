读完本章，你应能画出一个 Agent 的完整执行闭环，解释为什么工具结果会反复收费，给整个任务设置可执行的预算，并判断增加模型或子 Agent 是否真的改善了效率。

这里的 harness 指模型外部的运行系统：它保存状态，构建上下文，分发工具，处理错误，累计用量，决定是否继续。模型决定什么，程序决定什么，两者的边界本身就是研究变量。

## 8.1 Agent 的成本是整条轨迹的成本

单轮问答通常是“问题进、回答出”。Agent 会进行“观察环境—提出动作—执行工具—观察新结果”的循环。ReAct 是把推理与行动交替组织起来的代表工作；这个交互方式解释了为什么只统计最后一段答案会漏掉大量成本。[ReAct 论文](https://arxiv.org/abs/2210.03629)

例如修复一个小程序，最终回答只有“已修复，测试通过”，但过程中可能读过 20 个文件、打印过两次完整日志、试过三种错误补丁，并让另一个模型总结了历史。如果只记最后 10 个 token，就无法评价这次任务是否经济。

设所有模型调用构成集合 $`\mathcal C`$ ，其中包括主模型、摘要模型、路由模型和子 Agent。对调用 $`c`$ ， $`I_c`$ 为完整输入长度， $`O_c`$ 为完整输出长度，则：

```math
N_{\rm task}=\sum_{c\in\mathcal C}(I_c+O_c).
```

同一段文字先由一个模型生成，再被另一个模型读取，会在生成端和读取端分别计入；这是两次实际处理，不是错误的重复记账。同一请求的 usage 字段被采集两次则是日志重复，必须去重。

工具程序产生的字符串本身不是模型生成输出。它在送进后续模型请求时才成为模型输入。如果工具内部也调用了 LLM，则内部调用另入账。没有暴露内部 usage 的工具不能假设为零，应标记“内部模型用量未知”。

## 8.2 持久状态和聊天历史不是同一个东西

聊天历史适合记录“发生过什么”，但下一步往往只需要“现在什么是真的”。假设上次修改前有 5 个失败测试，修改后只剩 1 个。若把新旧日志全部平铺给模型，它必须重新推断哪个状态有效；若只写“测试有失败”，又丢了具体目标。

一个可检查的状态结构可以是：

```json
{
  "goal": "修复空列表输入的错误",
  "current_revision": "revision_3",
  "facts": [
    {"claim": "empty_input 测试仍失败", "evidence": "logs/run_3:42"}
  ],
  "completed": ["已复现错误", "已定位输入检查"],
  "pending": ["检查零长度分支", "运行相关回归测试"],
  "artifacts": ["src/parser.py", "logs/run_3"],
  "remaining_budget": 4200
}
```

这是一份教学数据。实际状态更新要保留证据版本，让“新观察推翻旧事实”可以追踪。完成项最好来自工具结果或可检验产物，不能因为模型说“完成了”就自动成立。

形式上，环境真实状态为 $`e_t`$ ，模型目前知道的状态为 $`s_t`$ ，新观察为 $`o_t`$ ，harness 使用更新函数：

```math
s_{t+1}=u(s_t,a_t,o_t),\qquad c_{t+1}=g(s_{t+1},x).
```

$`a_t`$ 是刚执行的动作， $`u`$ 管理长期状态， $`g`$ 选择下一次模型输入。这个结构不保证 $`s_t`$ 足够表示环境。关键检查是：保留的信息是否足够选择正确动作，遗漏内容能否按需恢复。需要完整历史的任务不能强行套用极短状态。

为方便调试，先让 $`u`$ 尽量采用确定性操作：用最新测试结果更新失败 ID，用文件哈希标记版本，用结构化字段更新预算。确实需要自然语言判断的部分再交给模型。这样你既能减少重复阅读，也更容易找出错误来自模型还是状态程序。

## 8.3 工具输出应该服务于下一步决策

工具默认返回“所有数据”，未必返回“本次决策需要的数据”。最直接的优化是在程序侧过滤和聚合，然后给模型紧凑结果与恢复详细证据的位置。

Anthropic 的工程文章展示了用代码调用工具、按需加载工具定义、在运行环境中过滤数据再交给模型的做法。它支持这种系统设计思路，文中的示例节省比例不能当作所有工具任务的保证。[Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)

例如 100 条测试记录，每条包含很长的日志。用户当前只问“哪些测试失败了”。程序可以精确返回：

```json
{"total": 100, "failed": [7, 81], "details": "logs/test-run-17.json"}
```

这里 `total` 和失败 ID 来自精确计算，`details` 指向完整结果。如果下一步要定位第 7 个测试的异常，就读取它的报错、堆栈和附近代码。初次返回紧凑索引并不意味着永远隐藏细节。

过滤设计最容易犯三个错误：只保留日志开头导致关键错误在末尾被截掉；只保留错误文本导致模型看不到触发条件；去重时合并了来自不同版本的结果。一个实用返回结构应包含结果计数、选中项、截断标记、原始记录位置和版本。若数据超过上限，明确写“只展示前 20 项，共 93 项”，不要使模型误以为只有 20 项。

工具定义也占输入预算。先给工具目录，再加载本次需要的 schema，可能比每轮塞入几百个完整定义更经济。但发现工具也有调用和输入成本，而且模型可能因目录过于简略选错工具。比较时要计入发现过程及选错后的恢复。

还有一种常见节省：不要让模型逐行复制数据。程序可以直接将工具 A 的结果传给工具 B，模型只提出操作和读取回执。对于复制、连接、排序、求和等明确操作，这通常是更容易验证的数据通道；程序执行时间和错误恢复仍进入端到端测量。

## 8.4 预算必须约束完整调用

“最多生成 1000 token”限制的是一次调用的输出，无法限制包含十次调用的任务总量。一个可执行的任务预算至少要管住：累计输入与输出、下一次输入、最大输出，以及最后回答所需的保留量。

设总预算为 $`B`$ ，已消耗为 $`S`$ ，即将发送的完整输入为 $`I`$ ，本次输出上限为 $`O_{\max}`$ ，最终回复保留量为 $`R`$ 。发送前应满足：

```math
S+I+O_{\max}+R\leq B.
```

如果输出上限只是模型遵循的软提示，该式也只能形成软预算。需要严格预算时，运行后端必须能够执行输出上限，并在用量缺失时保守停止。输入包含工具定义和序列化开销，估计低了也会造成超支；实际工程可使用目标分词器预数并留余量。

所谓最终回复保留量，也包含最终调用的输入。如果剩下 100 token，却需要把 3000 token 上下文再次送给模型，最终回答依然发不出去。可以预先构建紧凑的最终状态，或者用确定性的程序返回停止状态。

预算不够时，harness 应把任务标为 `budget_exhausted` 或“部分完成”，保留已完成证据和剩余项。把“因为预算停止”记录为成功，会使低预算方案在报表上看起来异常优秀。

多 Agent 并行时还要增加**已预约但尚未结算**的量 $`A`$ ：

```math
S+A+I+O_{\max}+R\leq B.
```

每个子调用在发出前原子地预约预算，返回后按实际 usage 结算并释放多余预约。若只看已经花掉的 $`S`$ ，四个并发调用可能同时认为“还剩 1000”，然后一起超支。下面的示例是串行预算教学，不实现并发原子预约，也不声称是生产级网关。

## 8.5 路由：便宜模型不一定更省 token

路由器根据任务或当前状态选择模型。小模型的每 token 计算或价格可能更低，却可能输出更长，失败后还要升级大模型。研究 token 效率时必须核查总量；研究费用效率时则加入价格权重。

RouteLLM 研究通过偏好数据学习在强弱模型之间进行选择，目标是响应质量与费用之间的平衡。这是学习路由的一手参考，不证明选择弱模型必然减少 token。[RouteLLM 论文](https://arxiv.org/abs/2406.18665v4)

设 $`r(x)\in\{0,1\}`$ 为路由决定，1 表示强模型。若只调用一个被选模型，平均 token 为：

```math
\mathbb E[N]=\mathbb E[N_r(x)+(1-r(x))N_w(x)+r(x)N_s(x)].
```

$`N_r`$ 是路由本身的模型推理用量， $`N_w,N_s`$ 是弱、强模型的完整调用用量。路由器如果是一个不生成文本的分类器，应另计它的编码计算与延迟，并说明这里的 token 账覆盖范围。若策略是“先弱后强”，弱模型失败的路径必须同时计入两次调用和判断是否升级的成本。

路由信号可以来自输入长度、任务类型、可观察的错误码，或在开发集上训练的难度预测器。真实部署时不能读取正确答案或最终成功标签。用测试集结果寻找最佳阈值，再在同一测试集宣称改善，也会产生选择偏差。

一个合理比较包含：总是弱模型、总是强模型、随机路由、简单规则路由、学习路由。报告质量、完整 token、费用、延迟和升级率。路由收益可能来自“困难样本分配了更多资源”，也可能只是“强模型样本少了”；这些机制需要分开解释。

## 8.6 多 Agent：并行时间和通信 token 各有一本账

把一个任务拆给多个 Agent，有机会并行查不同文件或独立验证不同假设。它也引入任务说明、重复背景、子任务结果、协调讨论和整合回答。若每个 Agent 都重做同一搜索，再长篇互相复述，墙钟时间可能下降，总 token 却上升。

考虑一个非常简化的通信模型： $`k`$ 个工作 Agent， $`r`$ 轮交流，每个 Agent 每轮生成一条 $`m`$ token 消息，每条被其余 $`k-1`$ 个 Agent 各读一次。暂忽略历史重放、协调者和实际工作，则：

```math
N_{\rm generated}=krm,
\quad N_{\rm read}=k(k-1)rm,
\quad N_{\rm comm}=k^2rm.
```

一个协调者分配任务、收集结果的星形拓扑，在“每个工作 Agent 每轮收到一条独立任务、发回一条同长结果，每条都生成一次、读取一次”的假设下，通信量为 $`4krm`$ 。这里不是在证明星形拓扑始终更省：当 $`k=4`$ 时两者正好相等；当背景和消息长度不同、需要反复协商时，公式也会变化。它只展示了要把**每条消息在哪里生成、被谁读几次**写清楚。

最容易执行的通信协议是：给每个子任务一个明确问题、输入范围、结束条件和简短输出结构；共享完整材料的位置；只传结果、证据和未解决冲突。子 Agent 返回“通过”不够，应返回“检查对象、检查方法、观察结果、证据位置”。简洁不能删掉结论所需的依据。

并行的延迟近似是最长路径上的执行时间加调度、整合开销；总计算则更接近所有实际执行工作的总和。二者没有理由同步下降。评估多 Agent 时，应与**相同总预算下的单 Agent**比较，另给相同墙钟限制的比较，说明自己改善的是哪一种约束。

## 8.7 动手：预算、路由、通信与工具筛选

执行：

```bash
python3 examples/agent_budget_lab.py
```

这是标准库合成演示，没有调用真实 Agent。主要输出包括：

| 演示 | 默认运行结果 | 能说明什么 |
|---|---|---|
| 调用前预算检查 | 两次调用后花 670；第三次拒绝；最终总量 770，预算 1000 | 先预留最大用量，再按实际用量结算 |
| 路由阈值 0.6 | 合成成功率 0.9，平均总量 340 | 分配资源可以形成一条质量—成本曲线 |
| 总选强模型 | 合成成功率 0.9，平均总量 520 | 对照组也计入同一 20 单位路由开销，便于隔离选择机制 |
| 四工作 Agent、三轮、消息长 100 | 全互联生成 1200、读取 3600，共 4800 | 生成与多次接收分别入账 |
| 精确筛选工具结果 | 空白分隔单位从 4600 到 5；保留失败 ID 7 和 81 | 程序聚合能减少进入上下文的数据 |

路由演示的人为难度特征与人为成功标签故意高度相关，所以阈值 0.6 看起来很好。这不构成对真实路由器的验证。代码的价值在于让阈值、选择结果和成本公式完全可见。

真实的“总选强模型”部署通常无需运行路由器，因此应另给移除 20 单位路由开销的对照。这也提醒我们：为了控制变量而构造的教学对照，未必是实际工程里最强的 baseline。

工具筛选使用 Python 精确找出失败 ID。5 个空白分隔单位不是实际 tokenizer 的 5 个 token；它也只适用于“哪些失败”这一查询。如果任务要求诊断失败原因，就需要更多信息。

## 8.8 怎样把教学系统升级成有效实验

先冻结模型、任务集、工具版本与成功判定，然后按以下顺序增加变量：完整工具结果；程序筛选结果；显式状态；任务预算；路由；多 Agent。每加一项都记录它对任务路径的影响，包括工具次数、失败恢复和停止原因。不要把六项同时更改后仅归因于某一个“智能记忆模块”。

用量日志至少应带 `task_id`、`call_id`、父调用、模型版本、输入、输出、缓存字段、结束原因和时间。隐藏推理若已包含在输出 usage 里，不要再次加；若 API 只给出部分输出计量，明确覆盖不足。相同样本的不同方案尽量从同一环境快照开始，避免一个方案读到另一个方案已经修改过的文件。

重点查看三类反例：筛选删掉唯一错误线索；压缩状态把过期事实当成当前事实；预算阻止了必要验证。只有总 token 下降而任务验收仍满足要求时，才有依据声称改善了本教程关心的前沿。

## 8.9 练习与参考答案

1. 总预算 5000，已结算 2600，两个并发调用已预约 1000，新调用输入 500、最大输出 600，最终保留 400，能否发送？
2. 五个工作 Agent 交流两轮，每条消息 80 token。在本章全互联假设下，通信总量是多少？星形假设下呢？
3. 弱模型一次花 300 token，失败率 0.4；失败后强模型花 900；判断是否升级花 50。忽略其他差异，先弱后强的期望总量是多少？
4. 将工具筛选示例改成“只显示第一个失败”。构造一个必须知道第二个失败才能正确决策的任务，并解释为什么压缩比不是充分指标。

参考答案：第 1 题为 $`2600+1000+500+600+400=5100`$ ，不能发送。第 2 题全互联为 $`5^2\times2\times80=4000`$ ，星形为 $`4\times5\times2\times80=3200`$ ，但这不比较任务质量。第 3 题为 $`300+50+0.4\times900=710`$ ，还需验证升级判断是否可靠以及总成功率是否达到要求。
